# Effect runtime ownership

Updated 2026-09-06 for AUDIT.md phases 6 and 7. This is a source map, not a new execution protocol.

| Responsibility                                       | Dependencies and reads                                                                | Mutation and ordering owner                                                                                                                                                                                                                     |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Selectors (EffectQueries)                            | Read-only draft players, entity/card lookup, derived stats, filters, frame creation   | Original frame target cursor, preserved selections and random-exclusion set; shared RNG. The runtime's step callback records the original budget/path.                                                                                          |
| Numeric values (EffectQueries)                       | Numeric references, selectors, conditions, destroyed-weapon snapshots                 | Shared RNG for random values, original frame and budget effects through selection. No new state copy or RNG.                                                                                                                                    |
| Conditions (EffectQueries)                           | State/history, events, numeric values and selectors                                   | No direct draft writes; delegated evaluation retains any selection/RNG side effects. Conditions are not universally pure.                                                                                                                       |
| Authored traversal (EffectRuntime)                   | Block conditions, choices, repeat/then branches and action arrays                     | One ResolutionQueue, active frame, diagnostic paths, trigger stack, budget and death checkpoints. Execution remains synchronous, including nested work.                                                                                         |
| Mana actions (mana-actions.ts)                       | Player selection, numeric evaluation                                                  | Only selected player mana/overload fields; trace and semantic event callbacks stay runtime-owned. Gain/destroy evaluate inside the player loop; overload evaluates once before it; unlock does not evaluate amount.                             |
| Summon actions (summon-actions.ts)                   | Catalog, selectors, placement policy, source snapshots and shared RNG                 | createMinion retains board capacity checks, entity allocation, insertion, events and triggers. The family owns local loop indices and event redirection after successful creation. Failed summons preserve original RNG use and index behavior. |
| Other action families (EffectRuntime)                | Targets, card zones, enchantments, history, replacement events and entity helpers     | Central mutation helpers, allocations, semantic emission and death processing. Their coupling to replacement/death/continuous ordering warrants separate evidence before further extraction.                                                    |
| Combat (EffectRuntime)                               | Derived attack/keywords, targets, replacements, weapon durability and damage outcomes | Same resolution context owns damage, combat/event correlations, trigger ordering, deaths and combat counters. Renderer presentation is outside this domain.                                                                                     |
| Continuous derivation (EffectRuntime)                | Live sources, auras, enchantments, selectors/conditions and base stats                | Deriving guard and ordered draft stat/keyword/cost recomputation remain central. Queries borrow this state; they do not cache independent mutable copies.                                                                                       |
| Resolution boundary (EffectRuntime and match facade) | Initial state, seeded RNG and returned resolution                                     | Runtime owns its draft, RNG checkpoint, counters, trace and event arrays. Facade validates an isolated committed copy and restores previews/failures. Public masking and returned snapshots remain separate.                                    |

## Incremental content types

ManaCardAction discriminates gain-mana, destroy-mana-crystal, overload and unlock-overload. Gain/destroy require player and amount; overload requires amount; unlock requires neither. Player, crystal and duration use existing vocabularies. Amount retains finite signed numbers, full, random arrays, condition/thenValue/elseValue, and reference/operation objects supported by the validator. Finiteness, nonempty random arrays, selectors and condition semantics still require runtime validation.

All other action fields accepted by the existing validator remain available. Unmigrated discriminators are explicitly excluded from the mana union's fallback, so an invalid mana amount cannot escape into generic JSON typing. The existing card validator is unchanged and remains the content boundary.

Direct typed block actions use runValidatedAction; the same queue callback handles both typed and dynamic traversal. Dynamic choices, schedules, attached effects and hero-power adapters retain unknown-input guards. Their mana adapter preserves player-ID compatibility, normalizes only fields used by the handler, and retains the original amount expression for evaluation at the original time. Both paths invoke one generic runManaAction implementation; no unknown record is asserted to be validated ManaCardAction.

This is deliberately partial typing. Summon selection/filter/source structures and other nested effect data retain validation and runtime inspection. Their remaining checks protect broader contracts; removing them solely to type another family would extend this change into selector/schema redesign.
