## 4. Reuse the actual game rules for simulation

The preferred architecture is:

    Existing authoritative game rules
        → copied simulation states
        → legal action generation and effect resolution
        → search and evaluation
        → selected action
        → normal live-game validation and execution

First establish whether the rules can run without PixiJS, DOM objects, animation timers, or network calls. If they cannot, make the smallest necessary separation. Do not build a second approximate implementation of every card.

Expose or adapt the operations needed to obtain a player observation, create an isolated simulation, list legal actions, apply an action, resolve pending effects, identify the next decision-maker, and report a terminal result. These are responsibilities, not mandatory new function names.

A simulated action must use the same relevant rules as the live action: costs, targets, placement, buffs, auras, deaths, triggered effects, and turn transitions. Resolve effects to a valid decision boundary before asking the planner for another action.

Simulation must not change the live match, its random generator, entity-ID allocator, event listeners, or UI. Do not share mutable card instances or global state between branches. Test branch isolation explicitly.

Keep legal action generation separate from search pruning. The authoritative action list must be complete for the current decision. The planner can examine a subset, but it must not redefine what is legal.

Include choices and placement where relevant. Do not assume every decision is simply a card plus a target. Support whatever the existing game exposes, including attacks, hero powers, pending choices, and ending the turn.

Use the engine's actual turn owner. Multiple consecutive actions can belong to the same player. Do not alternate evaluation signs after every action as though each action passed control to the opponent.

## 5. Keep hidden information out of the decision system

**The AI must not use my hidden hand, secret identities, unknown deck order, or the live match's future random outcomes.** This restriction applies to the entire planning system, not just the evaluator.

Define the information boundary before connecting the search. The AI can use its own visible hand, public state, revealed history, and information explicitly available under the game's rules. An unrevealed secret is not a revealed secret just because the local process stores its identity.

Do not pass the real complete match to the planner and merely ask it to ignore hidden fields. Do not build hypothetical states by retaining the actual opposing hand or future draw order.

Construct planning inputs from permitted observations. If simulations require unknown cards, use documented hypotheses or samples consistent with permitted information. Do not assume the opposing deck list is known unless that is an explicit game rule. Keep deck composition and deck order separate.

For the first prototype, a limited public-information opponent-response model is acceptable. Label its omissions. Do not describe it as a complete hidden-hand model, and do not silently treat an unknown hand as a known empty hand.

If an unknown draw or effect cannot yet be sampled fairly, stop that branch at the uncertainty boundary and use an explicitly documented approximation. Do not consult the real hidden result to make the simulation continue.

Do not start by implementing a large belief-learning system. A fair, limited baseline is preferable to an apparently strong opponent that cheats.

Add a test with two live positions that have the same AI-visible information but different hidden hands or deck orders. The planning observations must match. With a fixed search seed and work budget, decisions must not change because of those hidden differences. Ensure that caches and debug helpers do not reintroduce the leak.

## 6. Search sequences, then execute one action at a time

Search the AI's remaining turn as a sequence of legal actions. Do not choose each action solely from its immediate reward.

Treat ending the turn as an actual transition. Resolve end-of-turn and start-of-turn effects according to the engine. Do not evaluate an invented “end turn” position that skips these consequences.

Start with current-turn search. Once it works, add a bounded opponent-response pass for the most promising candidate lines. Prioritize replies available from public information. Extend into the AI's following turn only when justified by the remaining budget.

Keep the distinction between a tactical guarantee and an estimate. A winning line that relies on an unknown secret or a favorable random outcome is not proven lethal.

Have the planner retain a best-so-far legal action throughout its work. A suggested continuation can accompany it for reuse and diagnostics, but it is not an instruction to execute the whole sequence blindly.

Execute one action through the normal game controller. Wait until its required effects resolve. Obtain the new observation and verify whether the continuation is still applicable. Replan after relevant new information, random outcomes, or choices.

Attach a match ID, turn ID, request ID, and state revision to planning requests and responses. Reject stale results. Recheck legality immediately before execution. Search code must never bypass the live engine's validation.

When time expires, use the best applicable legal action already available. If it is unavailable, use a cheap deterministic fallback. End the turn only when ending it is legal. A pending mandatory choice needs a valid choice, not an invalid end-turn command.

Handle mulligan or other entry-phase decisions through the existing controller if they are required to start a playable match. Use a simple bounded fallback initially; do not let opening-hand optimization expand the main task.

## 8. Handle chance explicitly

Separate decision choices from random outcomes. The AI chooses actions; it does not choose which random damage target or draw will occur.

Use exact outcome probabilities when cheap, or reproducible sampling when necessary. Use the game's actual random rules. Keep simulation randomness separate from live-match randomness.

For search evaluation, aggregate sampled outcomes or apply a documented risk rule. Do not keep only the favorable outcome and score it as guaranteed. Separate reproducible test seeds from knowledge of a live game's future.

If MCTS is selected, use bounded continuations or a suitable leaf evaluator. Do not assume uniform random play will meet the desired quality within the deadline. Keep evaluator scores and exploration settings on compatible scales.

Do not treat an unfinished simulation as a draw solely because a rollout limit was reached. Mark the cutoff and evaluate the position appropriately.
